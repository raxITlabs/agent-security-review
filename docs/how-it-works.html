agent-security-review

How an ast-grep rule pack turns AI-agent code into architectural security guidance — not just a list of bugs.

46 rules · 8 components · Python & TypeScript · worked example: a vulnerable LLM agent

This pack scans agent / LLM / MCP code and, for every issue it finds, tells you the design change that removes the whole class of problem — not a one-line patch. This page explains the machine, the thesis behind it, and walks a real scan of a deliberately-vulnerable agent end to end.

1. The core idea (the thesis)

Most scanners answer “where is the bug?”. This pack answers a harder, more useful question: “what about the architecture let this bug exist, and what shift removes it?” Every rule is tagged with one of three architectural shifts — Scope, Sign, Stop — and every finding carries an Architectural fix: that names a design move.

SCOPE

Shrink what the agent can do. Bound loops, split God-Agents, cap tool breadth, attribute retrieved data, avoid lethal capability combos.

SIGN

Establish who is acting. Per-task identity, no ambient credentials, signed agent-to-agent calls, authenticated gateways, secrets from a vault.

STOP

Gate what happens. A reference monitor before tool dispatch, no LLM output into sinks or control flow, moderation, no secrets in logs.

Scope / Sign / Stop is the spine: it maps to the lethal-trifecta & Meta Rule-of-Two work, DeepMind’s CaMeL (don’t let untrusted data steer the program), and AWS/Cedar reference-monitor patterns. The full mapping is in docs/FRAMEWORKS.md.

2. How a scan actually runs

The engine is ast-grep — it matches the code’s syntax tree (not regex over text), so it sees real structure: a decorated function, a tool dict, a call with or without a given keyword argument.

your repo→ fetch rules (live from GitHub main)→ ast-grep scan→ JSON findings→ report.py→ triaged report
  1. Resolve & fetch rules. scan.sh pulls the latest rules from the repo (with an offline fallback), so every scan uses current checks without re-installing.
  2. Scope the scan. Test / eval / example / fixture dirs are excluded by default — a fake key in a test isn’t shipped attack surface. (--include-tests overrides.)
  3. Match structure. ast-grep applies all 46 rules across the tree and emits JSON: rule id, severity, file:line, the matched code, and metadata (shift + confidence).
  4. Cover the prompt surface. ast-grep has no Markdown parser, so a companion scan-markdown.sh grep-pass catches injected instructions planted in .cursorrules / SKILL.md / CLAUDE.md.
  5. Triage. report.py groups by severity, shows each rule’s architectural fix, and prints a confidence summary so heuristic findings read as “triage first”, not “block the build”.
Deterministic floor, human ceiling. The scan is the reproducible floor. The skill that wraps it also has the model read the code for what fixed patterns can’t see, and — critically — classify whether the repo is even an agent. On a non-agent repo it scopes out instead of inventing findings.

3. Worked example — scanning a vulnerable LLM agent

Our example is damn-vulnerable-llm-agent (dvla) — a LangChain banking agent built intentionally insecure. Running the pack:

# from the pack repo
ast-grep scan --config sgconfig.yml --include-metadata --json ./dvla
# → 4 findings: 2 error, 2 warning

Here is the actual output, finding by finding.

stop.llm-output-to-dangerous-sink ● error STOP confidence: high
wheretransaction_db.py:62 & :76 codecursor.execute(f"SELECT * FROM Transactions WHERE userId = '{str(userId)}'") whyAn agent tool runs an f-string SQL query built from a value the LLM controls. A prompt-injected model can rewrite the query → data exfiltration / tampering. This is the LLM-output-to-sink class.
Architectural fix (Stop): never pass model/tool output into a code or shell sink; use parameterized queries and put a reference monitor at the tool boundary.
A point-fix scanner would say “escape this string.” The architectural fix says the agent should never be able to reach a raw SQL sink at all — that kills every future instance, not this one line.
scope.god-agent-tool-count ● warning SCOPE confidence: medium
wheretools.py:22 & :40 codeget_current_user_tool = Tool(name='GetCurrentUser', …) whyMany powerful tools registered to one agent — the “God-Agent” pattern. The more an agent can do from one context, the larger the blast radius when it’s hijacked.
Architectural fix (Scope): split into polyphonic specialized agents, each with a narrow tool list — so a compromise of one can’t reach everything.

4. Reading the report

report.py turns those raw matches into a prioritized, honest summary:

## Security scan: 4 finding(s) — 2 error · 2 warning

_Confidence: 2 high · 2 medium. Low-confidence findings are heuristic — triage first._

### ERROR (2)
- stop.llm-output-to-dangerous-sink  `control-flow/stop`
  - transaction_db.py:62  — LLM-driven SQL sink
  - Fix: parameterized queries + reference monitor at the tool boundary

### WARNING (2)
- scope.god-agent-tool-count  `agent/scope`
  - tools.py:22 — God-Agent tool sprawl
  - Fix: split into specialized agents with narrow tool lists

5. Why precision matters to the thesis

Architectural guidance is high-stakes: telling someone to re-architect a false positive trains them to ignore you. So the pack is built to keep the advice trustworthy:

GuardrailWhat it prevents
Applicability gateOn a non-agent repo (a training library, a CLI) the scan scopes out — it won’t manufacture “missing gateway auth” for code that has no gateway.
Confidence tiersHeuristic rules carry confidence: low/medium so a “maybe” never reads like a “must.”
Generalized, not repo-shapedRules key on portable signals (canonical names, call shapes, sink kinds) — validated across LangChain, LangGraph, OpenAI Agents, CrewAI, Bedrock, MCP — not one repo’s literals.
Router-aware authReal example: the gateway rule learned to recognize router-level auth (APIRouter(dependencies=…)) after a scale test on a large agent platform showed ~40% of its hits were centrally-authenticated routes.
